# v0.2.0-alpha.1 installation and operations runbook

This runbook intentionally uses placeholders. Never paste a database URL,
admin token, Telegram token, webhook secret, recipient, or message body into a
ticket, transcript, smoke-test output, or committed file.

## Install

From the checked-out release commit, install exactly the locked dependencies:

```bash
uv sync --frozen --all-extras --group dev
uv run python -c "import personal_assistant; print(personal_assistant.__version__)"
```

The expected version is `0.2.0-alpha.1`. Load secrets from the deployment
secret store or ignored `.env`; do not pass them as command arguments.

## Migrate

Back up the target database according to its normal retention policy. With
`DATABASE_URL`, `DATABASE_SCHEMA`, and `APP_ENV_FILE` supplied through the
process environment:

```bash
uv run python -m personal_assistant.infrastructure.migrations status
uv run python -m personal_assistant.infrastructure.migrations apply
uv run python -m personal_assistant.infrastructure.migrations status
```

The final status must be ready with no pending migration. Stop if a checksum,
history, or connectivity error appears; do not edit migration history by hand.

If upgrading a database that may contain traces written before external
identifier pseudonymization, run the read-only historical trace inspection
before startup:

```bash
uv run python -m personal_assistant.infrastructure.trace_sanitizer
```

After a backup and operator review, a rewrite requires the explicit
`--apply --confirm SANITIZE_TRACES` gate documented in the persistence runbook.

## Start

Set `PERSISTENCE_BACKEND=postgres`. If durable delivery is enabled, also set
`REMINDER_WORKER_ENABLED=true`, a worker interval, a heartbeat timeout greater
than the normal interval, and the Telegram configuration through the secret
store. Bind the application to loopback:

```bash
uv run uvicorn personal_assistant.infrastructure.http:app --host 127.0.0.1 --port 8000
```

The public reverse proxy may expose only the authenticated Telegram webhook.
It must not expose `/livez`, `/readyz`, `/healthz`, `/admin`, or `/admin/*`.

## Smoke test

Do not send a Telegram message. From the same host:

```bash
curl --fail --silent http://127.0.0.1:8000/livez
curl --fail --silent http://127.0.0.1:8000/readyz
```

Expect HTTP 200 from both. When the worker is enabled, readiness may briefly be
503 until its first heartbeat. It must become ready within one normal worker
interval. Authenticate `/admin/metrics` using an in-memory Authorization
header, verify its response has only `counts` and `health`, then clear the shell
variable. Never print the header value.

Run the release gates without real providers. The reliability cases use the
local PostgreSQL configured through a pre-existing `TEST_POSTGRES_DSN`:

```bash
APP_ENV_FILE=disabled LLM_PROVIDER=disabled TRANSCRIPTION_PROVIDER=disabled \
TTS_PROVIDER=disabled TELEGRAM_BOT_TOKEN= \
uv run python -m personal_assistant.evals --suite eval/cases
uv run pytest -q
```

The eval summary must report `293/293 passed`.

The complete PostgreSQL test gate also requires `TEST_POSTGRES_DSN` to already
exist in the process environment. If that DSN intentionally omits its password,
provide `PGPASSWORD` through the same local secret mechanism. Do not echo either
value or place it in command history. Without `TEST_POSTGRES_DSN`, the
PostgreSQL reliability eval gate fails closed; the result is not release
evidence.

## Controlled bot acceptance smoke

The automated suite does not call Telegram. After all offline gates pass, the
release operator executes this smoke using local, secure credentials for a
dedicated test bot and non-personal test recipient.

This is an acceptance gate for the prerelease, not an optional quality check.
The prerelease must not be published without either the passing evidence below
or an explicit, dated waiver from the release owner that records the reason and
accepted risk. Lack of local credentials is not itself passing evidence.

1. Record the local timezone and an explicit local wall-clock time in private
   operator notes. Schedule one harmless test reminder far enough ahead to
   allow a restart before it becomes due.
2. Submit one test update, then replay the exact same provider update ID and
   payload. Confirm the workflow/outbox counts did not duplicate.
3. Restart the API and worker before the reminder becomes due. Wait for
   `/readyz` to return 200 with a fresh heartbeat.
4. Allow the reminder to become due and verify exactly one notification in the
   dedicated bot conversation. Do not paste its recipient or body into logs.
5. Query authenticated `/admin/metrics`: the response must contain only the six
   counts and health object. Confirm that no body, recipient, update ID, message
   ID, tenant ID, or provider credential appears.
6. Allow at least one subsequent worker tick. The notification count must
   remain exactly one and no row may be left in `claimed`, `sending`, or
   `uncertain`.

Pass criteria are: one accepted logical workflow, exactly one external
notification after replay and restart, fresh readiness, no unresolved delivery,
no sensitive content in the metrics response, unchanged webhook
configuration, a removed temporary schema, and an ACL-restricted ignored
credential file. Any duplicate, stale readiness, unresolved state, webhook
mutation, cleanup failure, or content leak fails the release smoke.

The `2026-07-27` release acceptance passed these criteria with 257 smoke
assertions. This count is distinct from the 293 deterministic eval cases. The
Phase 5 acceptance ledger is the authoritative sanitized evidence record.

## `uncertain` delivery

An `uncertain` row means the external send may have succeeded even though the
local commit outcome is unknown. Never retry it automatically.

```bash
uv run python -m personal_assistant.infrastructure.worker list-uncertain
```

Verify delivery using the provider's trusted operator console without copying
recipient/body data into logs. Resolve only with exact confirmation:

```bash
uv run python -m personal_assistant.infrastructure.worker resolve-uncertain \
  --message-id '<operator-selected-id>' --resolution delivered \
  --confirm '<same-id>'
```

Use `--resolution retry` only after confirming non-delivery. The command is
bounded by the existing attempt policy.

## Rollback

1. Stop ingress and the worker; preserve the database and operational logs.
2. Reconcile every `sending`/`uncertain` item before allowing an older worker to
   send. Do not make a blind retry.
3. Deploy the previously verified application commit and keep the database
   backup available.
4. Migration `0005` is additive and may remain during application rollback.
   Do not drop it during an incident. A later planned cleanup may remove it only
   after all new binaries are gone.
5. Start the old API with its worker disabled, smoke its liveness/readiness,
   then enable delivery only after the queue has been reviewed.

If rollback was caused by suspected secret exposure, keep ingress stopped and
rotate the affected secret before restart.
